# Версионирование и депрекация

## Purpose

Определить правила версионирования API и процесса депрекации изменений схемы.
Коннектор владеет контрактом, его потребляют 50+ сервисов, поэтому изменения схемы
должны быть предсказуемыми и управляемыми.

## Requirements

### Requirement: Версия API в пути

API SHALL быть версионировано через префикс пути (по умолчанию `/api/v1`). Смена
мажорной версии контракта SHALL вводить новый префикс (`/api/v2`) без немедленного
удаления предыдущего — в течение переходного периода обе версии доступны.

#### Scenario: Новая мажорная версия

- **WHEN** вводится ломающее изменение контракта
- **THEN** новый префикс `/api/v2` публикуется параллельно со старым `/api/v1`

### Requirement: SemVer для релизов коннектора

Релизы коннектора SHALL следовать SemVer. Ломающее изменение контракта (удаление
или переименование поля, изменение типа значения, удаление операции, изменение
семантики) SHALL увеличивать major-версию.

#### Scenario: Обратно совместимое изменение

- **WHEN** добавляется новое поле или операция
- **THEN** это minor-изменение, существующие потребители не ломаются

#### Scenario: Ломающее изменение

- **WHEN** поле удаляется/переименовывается или меняется тип значения
- **THEN** это major-изменение и должно пройти процесс депрекации

### Requirement: Процесс депрекации

Ломающее изменение SHALL пройти депрекацию: объявление `Deprecated` в changelog →
период депрекации (минимум один релиз) → удаление (`Removed`). Поле/операция,
помеченные как deprecated, MUST продолжать работать в течение периода депрекации.

#### Scenario: Депрекация поля

- **WHEN** поле объявляется deprecated
- **THEN** оно остаётся рабочим минимум один релиз до удаления, изменение отражено
  в `CHANGELOG.md`

### Requirement: Changelog

Каждое изменение контракта SHALL фиксироваться в `CHANGELOG.md` с секциями
`Added` / `Changed` / `Deprecated` / `Removed`.

#### Scenario: Запись об изменении

- **WHEN** вносится изменение контракта
- **THEN** в `CHANGELOG.md` появляется соответствующая запись

### Requirement: Уведомление потребителей

Перед релизом ломающего изменения потребители (50+ сервисов) SHALL быть уведомлены
заранее через change-proposal и changelog.

#### Scenario: Анонс ломающего изменения

- **WHEN** планируется ломающее изменение
- **THEN** создаётся change-proposal и уведомляются потребители до релиза
